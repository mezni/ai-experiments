# ADR-001: LlamaIndex + ChromaDB as the RAG stack

- **Status:** Accepted
- **Date:** 2026-09-01

## Context

The sibling project `01-rag-naive` proved the RAG DataOps concepts (hashing,
metadata, versioning) with a hand-written, pure-Python pipeline and a FAISS
index. Extending that design to more sources and operations, we need a
framework for loading, chunking, embedding, and retrieval, plus a durable
vector store.

## Decision

Use **LlamaIndex** as the RAG framework and **ChromaDB** as the single vector
store:

- Document loading, chunking (`NodeParser`), and vector-store integration come
  from LlamaIndex (`llama-index-core`, `llama-index-vector-stores-chroma`).
- All vectors and per-chunk metadata live inside ChromaDB collections.
  ChromaDB is the *only* vector store: there is no FAISS index and no JSON
  file store for vectors or chunk metadata.
- Embeddings go through OpenRouter's OpenAI-compatible gateway (the `openai`
  client), so the embedding model stays configurable per snapshot.

## Consequences

- The hand-written chunking, index math, and persistence from `01-rag-naive`
  are replaced by maintained libraries.
- ChromaDB's `PersistentClient` gives us on-disk snapshot directories, keeping
  "full snapshots per index version" cheap to implement (see ADR-002).
- JSON is reserved for the index registry and document catalog only.
- Cost/complexity trade-off: the framework brings many transitive
  dependencies; we keep them to the core Chroma integration rather than the
  full `llama-index` meta-package.
