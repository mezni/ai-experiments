# Omni-Connect Retail Copilot — Architecture

## Overview

Omni-Connect is an AI-powered telecom retail copilot: a representative-facing
Streamlit workspace that surfaces customer context, grounds answers in a
curated company policy knowledge base, evaluates promotion eligibility, and
captures order decisions — with specialist agents orchestrating the reasoning.

The system is a **sandboxed, single-node Python application** (no external
databases, no distributed services). All state is either synthetic JSON under
`data/business_data/`, curated markdown under `data/knowledge_base/`, a local
FAISS index under `data/kb_store/`, or Streamlit session state. LLM calls go to
Anthropic (or an Anthropic-compatible provider via `LLM_BASE_URL`); embeddings
and reranking run fully locally with `sentence-transformers`.

```
┌────────────────────────────────────────────────────────────────────┐
│                        app/portal.py (Streamlit)                   │
│   Customer │                     Agent │              Decision     │
│   profile, billing,            chat, RAG citations,   next-best action, │
│   line, usage                  promos, shortcuts      delta, order      │
└──────────────┬────────────────────────┬────────────────┬───────────────┘
               │                        │                │
        src/services/*           src/agents/*,      (recommendation,
        (business-data          src/llm/*,          override, POS mock)
         lookups)               src/core/*          — portion of portal
                               src/mcp/*
┌──────────────┴────────────────────────┴───────────────────────────────┐
│  src/knowledge/*  — FAISS + BM25 hybrid RAG over data/kb_store/        │
│  data/            — synthetic business JSON · curated policy .md.txt    │
│  config/          — llm_config · agent_config · mcp_config · prompts   │
└────────────────────────────────────────────────────────────────────────┘
```

## Directory map

| Path | Responsibility |
|---|---|
| `app/portal.py` | Streamlit UI — the sole user-facing entrypoint |
| `src/services/` | ID-based lookups over `data/business_data/*.json` |
| `src/knowledge/` | Embeddings, FAISS `KnowledgeBase`, hybrid `Retriever` |
| `src/llm/` | `LLMClient` (Anthropic) + `PromptManager` (template loading) |
| `src/agents/` | Specialist agents: customer profile, policy, promotion |
| `src/core/` | `AgentCoordinator` (workflow runner) + `WorkflowValidator` |
| `src/mcp/` | Model Context Protocol server + client (single tool) |
| `src/utils/` | YAML config loader + logging setup |
| `scripts/` | Deterministic data generators + RAG pipeline CLI |
| `config/` | `llm_config.yaml`, `agent_config.yaml`, `mcp_config.yaml`, `prompts.py` |
| `data/` | Runtime datasets, knowledge corpus, FAISS index (gitignored output) |
| `docs/` | `brief.md` (business), `data.md` (schemas), `portal.md` (UI), `architecture.md` |

## Layers

### 1. Data layer (`data/`, generated by `scripts/`)

- **Category A — business data** (`scripts/business_data_generator.py`):
  `product_catalog.json` (plans + devices), `promotions.json`,
  `crm_records.json`, `billing_records.json`. Catalogs are hard-coded ground
  truth mirroring `docs/data.md`; person-level records are synthesized with
  `faker` honoring documented business rules. `usage_telemetry.json` is
  documented as *pending* and intentionally not generated.
- **Category B — knowledge base** (`scripts/knowledge_data_generator.py`):
  twelve curated policy/interaction documents (`*.md.txt`) each carrying
  canonical metadata (`Document ID`, `Version`, `Department`) that the portal
  and the RAG pipeline parse.

### 2. Service layer (`src/services/`)

Thin, stateless lookups over the JSON datasets:

- `customer_service.get_customer(id)` — CRM record (plan, eligibility, tenure).
- `catalog_service.get_plan(id)` / `get_device(id)` — catalog lookups.
- `billing_service.get_billing_account(id)` — device, autopay, invoices.
- `promotion_service.get_promotion(id)`.

Not-found lookups return an `{"error": ...}` dict rather than raising.

### 3. RAG / knowledge layer (`src/knowledge/`)

- `embeddings.py` — `EmbeddingGenerator` (BAAI/bge-small-en-v1.5, 384-dim,
  locally via `sentence-transformers`), pure-Python `BM25Index`,
  `Reranker` (BAAI/bge-reranker-base cross-encoder).
- `knowledge_base.py` — `KnowledgeBase`: document loading + chunking
  (1000-char chunks, 200 overlap), FAISS `IndexFlatL2` build/save/load.
- `retriever.py` — hybrid retrieval
  (`retrieval.method: "bm25+embedding+rerank"`): BM25 + FAISS candidates are
  merged and deduplicated by `(source, chunk_id)`, then re-scored by the
  reranker. Hits carry `{content, source, category, chunk_id, score}`.

The persisted index lives at `data/kb_store/vector_index.{index,docs}` and is
built by `scripts/rag_pipeline_runner.py build`.

### 4. LLM layer (`src/llm/`)

- `llm_client.py` — `LLMClient` wraps the Anthropic SDK. Key resolution order:
  `ANTHROPIC_API_KEY` → `OPENROUTER_API_KEY` → `OPENAI_API_KEY`;
  `LLM_BASE_URL` optionally routes through an Anthropic-compatible provider
  (e.g. OpenRouter). System messages are split into Anthropic's `system`
  parameter; `classify()` uses dedicated classification settings.
- `prompt_manager.py` — `PromptManager` loads templates from
  `config/prompts.py` (`get_prompt(name)`, `format_prompt(template, **kw)`).

### 5. Agent layer (`src/agents/`)

Each agent follows the bootcamp pattern: pull the needed context, format the
prompt, call the LLM, return a structured dict.

| Agent | Input | Output |
|---|---|---|
| `CustomerProfileAgent` | `customer_id` | usage/plan/line profile summary |
| `PromotionEvaluatorAgent` | `customer_id`, optional promo ids | per-promo eligibility checks + narrative |
| `PolicyRetrieverAgent` | question + optional context | grounded answer + per-source citations (RAG) |

`PromotionEvaluatorAgent` distinguishes hard **blockers** (account status,
expiry, win-back exclusivity) from informational **notes** (target
plan/device differ from current holdings) — plan offers exist to move a
customer onto the target plan, so a mismatch is not a hard stop.

### 6. Coordination layer (`src/core/`)

- `agent_coordinator.py` — `AgentCoordinator` wires the agents into named
  steps. `build_plan()` produces the default linear plan
  (`customer_profile` → `promotion_evaluator` → `policy_retriever:<question>`);
  `run_workflow(customer_id, policy_questions, plan)` executes steps,
  threading prior outputs into `context`, and aggregates results by step name.
  (`agent_config.yaml` declares the same sequence; the coordinator currently
  reads no config.)
- `workflow_validator.py` — `WorkflowValidator.validate(result)` returns a
  list of structural errors (missing/invalid required sections, or a section
  that carried an error payload) or `None` when the shape is valid.

### 7. MCP layer (`src/mcp/`)

A single Model Context Protocol capability over `stdio` (local subprocess, no
network): `mcp_server.py` exposes `get_customer_profile_tool` via FastMCP;
`mcp_client.py` provides the sync `fetch_customer_profile_via_mcp(customer_id)`
wrapper (notebook-safe via a dedicated thread event loop). Declared shape lives
in `config/mcp_config.yaml`.

### 8. Presentation layer (`app/portal.py`)

Streamlit workspace with three columns: **Customer** (selector, profile,
line/usage/billing context), **Agent** (copilot chat, promo eligibility cards,
RAG citation expanders, prompt shortcuts), **Decision** (scaffold
next-best-action rule, action/override capture, POS submission mock). Live
service lookups but an intentionally scaffolded copilot: chat answers, budget
telemetry, and the recommendation rule are placeholders.

## Configuration (`config/`)

| File | Role |
|---|---|
| `llm_config.yaml` | Provider, chat/embedding/reranker models, API timeouts, RAG retrieval settings |
| `agent_config.yaml` | Workflow plan, promotion evaluation rules, RAG paths, validation fields |
| `mcp_config.yaml` | MCP server name/transport, tool documentation, client timeout |
| `prompts.py` | Agent prompt templates (`customer_profile`, `compliance`, `lending_policy`) |

Environment (`/.env`, template in `.env.example`): `ANTHROPIC_API_KEY`,
`LLM_BASE_URL`, optional `HF_TOKEN`.

## Containerization

`Dockerfile` (python:3.13-slim) installs `requirements.txt` and runs the portal
on 8501; `docker-compose.yml` maps host 8502 → 8501, passes `.env`, and mounts
`./data` read-write so JSON/index files can be edited without rebuilds.
`docker compose config` validates; compose is aligned with the pinned
`mcp<2` constraint in both `pyproject.toml` and `requirements.txt`.

## Key design decisions

- **Local RAG, remote reasoning.** Embeddings and reranking are fully local
  (`sentence-transformers`); only chat goes to the LLM API. No embedding
  vendor lock-in, but the image is large (torch) and first model downloads
  need network. Prefer out-of-band `python scripts/rag_pipeline_runner.py build`
  to persist the index before first interactive use.
- **Bootcamp-proven agent pattern.** Specialist agents are composed by a
  coordinator/planner, matching Bootcamp 3. omni-connect replaces the loan
  underwriter with telecom specialists and a deterministic `build_plan()` in
  lieu of a PlannerAgent.
- **Hybrid retrieval as ground truth.** BM25 + FAISS + cross-encoder rerank
  produces the `policy_retriever` citations the portal answers are grounded in;
  the retrieval method is configurable in `llm_config.yaml`.
- **Errors are data, not exceptions.** Services return `{"error": ...}` dicts;
  the coordinator threads them into the workflow and `WorkflowValidator` flags
  error-carrying sections instead of crashing.
- **MCP kept to one tool.** A single, clean protocol example
  (`get_customer_profile_tool`) matches the bootcamp's Scope Decision 2, with
  `mcp<2` pinned because mcp 2.x renamed the FastMCP API the server uses.

## Known limitations (current scaffold state)

- **CWD-relative paths.** All config/data paths resolve against the working
  directory; run the app and scripts from the repo root.
- **Dual dependency manifests.** `pyproject.toml` and `requirements.txt` both
  pin direct deps; keep them in sync (uv is the source of truth for local
  installs; `requirements.txt` drives the Docker build).
- **`agent_config.yaml` and `mcp_config.yaml` are declarative only** — the
  coordinator/agents/server read matching in-code constants, not the YAML.
  The plan sequence and validation fields are the one exception the validator
  does read.
- Portal telemetry (latency/grounding score), the recommendation
  `recommend_next_best_action` rule, and copilot chat responses are mocks to be
  replaced by real agent + RAG wiring through `AgentCoordinator`.
- No automated test suite yet; validation is structural
  (`WorkflowValidator`) plus the `query`/`build` commands of
  `scripts/rag_pipeline_runner.py`.

## Operate

```bash
# Configure
cp .env.example .env            # fill ANTHROPIC_API_KEY; optional LLM_BASE_URL

# Generate + build once
python scripts/business_data_generator.py --count 10
python scripts/knowledge_data_generator.py
python scripts/rag_pipeline_runner.py build --query "Check trade-in rules"

# Run
streamlit run app/portal.py                     # local: http://localhost:8501
docker compose up --build                       # container: http://localhost:8502

# Ad-hoc RAG + MCP checks
python scripts/rag_pipeline_runner.py query "Refund window for new devices"
python -c "from src.mcp.mcp_client import fetch_customer_profile_via_mcp; \
print(fetch_customer_profile_via_mcp('CUST-531012'))"
```
